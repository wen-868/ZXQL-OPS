# 智享全链运营系统 · 总体规划

> 定位：独立新项目，专做**短视频 + 直播带货**运营。独立部署、独立库、独立进程，
> 不耦合智享全链管理系统 14 个微服务；但按管理系统**统一标准**建设，并预留**接入接口**。
> 本文整合全部规划，单一文档即为完整基线。

---

## 1. 设计原则

| 原则 | 说明 |
|---|---|
| 独立运营系统 | 独立部署/独立库/独立进程，代码不耦合管理系统 |
| 统一标准 | 技术栈、多租户、基础设施、认证、接口风格对齐管理系统 |
| 可接入 | 内置 ZhixiangCore 适配层，按管理系统契约预留接口；双模式(独立/联通)可切换 |
| 统一账号 | 与管理系统共享身份（SSO/OAuth2）；一个账号打通两系统，tenant 对齐 |
| 数据打通 | 联通模式下经 ZhixiangCore 适配层与管理系统双向实时打通（订单/库存/商品/财务/租户）|
| 功能归位 | 联通模式下重叠功能（库存/订单/物流/商品主数据/财务报表）在运营系统仅展示，写操作全部归管理系统；独立模式下运营系统全功能自营 |
| 聚合调用 | 能力网关 / Skill Gateway 统一编排 本地 Ollama + 外部大模型/视频服务 + 租户自建，源对用户体验透明（不标注本地/外部）|
| 弹性部署 | 默认本地 Ollama 可单台部署；外部/租户自建模型可选；业务平台 API 之外不强制出网 |

## 2. 技术架构

**技术栈**：NestJS + TypeScript · TypeORM + MySQL · Redis · RabbitMQ · Elasticsearch · MinIO · JWT · REST + SSE

**模块结构**
```
src/
├─ core/            统一标准：JWT 守卫 / 响应拦截 / 租户上下文
├─ integration/     ZhixiangCore 适配层（接入管理系统唯一通道，默认 stub）
├─ analyze/         人性分析（本地/外部 LLM）
├─ ideate/          选题
├─ script/          脚本工坊
├─ product/         商品内容中心
├─ selection/       选品中心
├─ publish/         发布与分发
├─ live/            直播中心（真人+数字人）
├─ ad/              投放/投流
├─ fans/            粉丝与私域
├─ revenue/         收益与对账
├─ talent/          达人/商单（MCN）
├─ orchestrator/    工作流编排（RabbitMQ + SSE）
├─ skill/           能力网关 / Skill Gateway（AI+媒体 多 Provider 路由+降级）
├─ service/         智能客服中心（AI 自动回复/工单/转人工）
└─ dashboard/       仪表盘 BI
```

**能力网关 / Skill Gateway（聚合 AI 与媒体能力，源透明）**
- Skill 类型：text-generate（原 LLM）/ video-generate（即梦/可灵/本地）/ image-generate / voice-clone / digital-human，统一抽象
- Provider：聚合编排 **本地 + 外部(openai/deepseek/qwen/glm/claude/即梦/可灵/...) + 租户自建(BYO)**，统一调用
- 路由：按 skill + 任务选 provider；外部失败降级本地；源对用户体验透明（不标注"本地/外部"）
- 租户 BYO：skill_providers 带 tenant_id，租户在技能中心(Z)/设置(P)自建接入自有模型/视频服务，key 不跨租户共享
- 安全：API Key 加密、不返前端；用量/成本日志(按租户)；限流超时

**ZhixiangCore 适配层（接入管理系统，双模式）**
- **统一账号（SSO）**：`ssoLogin` / `verifyToken` / `syncTenant` / `listAccounts`；运营系统经管理系统 OAuth2/SSO 登录，tenant 对齐，一个账号打通两系统
- **数据双向打通**：联通模式下订单/库存/商品/财务/租户与管理系统实时同步（读展示 + 写回推）
- Product：`listProducts` / `getProduct`（商品主数据读源，展示用）
- Order/Inventory：`queryOrder` / `queryStock` / `pushOrder`（读展示；挂车转化自动推单回管理系统）
- Commission/Finance：`queryCommission` / `queryFinancial`（财务报表展示）
- Callback：`POST /core/callback/order-settled`、`/stock-updated`、`/tenant-updated`、`/financial-updated`（管理系统→运营系统通知）
- **功能归位**：联通模式下 Y(库存/订单/物流)/R(商品主数据)/W(财务) 在运营系统**只读展示**，写操作经 SSO 深链跳管理系统或适配层代理；管理系统为唯一真源
- 约束：业务模块仅经适配层访问管理系统，禁直连；`integration_mode`(standalone/connected) 控制双模式

## 4. 功能明细清单

### A. 统一标准与管理系统接入 [Must]
- [ ] 统一技术栈 NestJS+TS+TypeORM+MySQL（独立库表）
- [ ] 多租户 tenant_id 隔离
- [ ] 复用 Redis/RabbitMQ/ES/MinIO
- [ ] JWT 统一认证 + 管理系统 SSO
- [ ] REST+SSE、统一响应体 `{code,message,data}`
- [ ] ZhixiangCore 适配层：Auth/Tenant/Product/Order/Commission/Callback
- [ ] 适配层 feature flag（默认 off）
- [ ] 业务仅经适配层访问管理系统

### B. 账号矩阵中心 [Should]
- [ ] 多平台账号 OAuth 接入（抖音/视频号/小红书/快手）
- [ ] 账号分组 / 人设档案
- [ ] 健康监控（限流/违规/权重）
- [ ] 矩阵看板 / Token 续期提醒

### C. 市场情报与竞品采集 [Must]

## 9. 关键设计要点

- **人性分析**：固定 7 人性 × 6 情绪字典，驱动选题/脚本/卖点/直播话术口径一致。
- **混合推理**：所有 AI 生成经能力网关 / Skill Gateway，本地 Ollama 默认，外部模型/视频服务按任务路由、失败降级。
- **直播双形态**：真人(RTMP+OBS 中控) 与数字人(能力网关驱动话术+弹幕 AI 应答)，渲染失败降级。

- **闭环**：J 回收评论/数据 → D 再分析 → E 优化选题权重，是相对普通创作者的本质优势。
- **独立但标准**：代码独立，规范对齐管理系统，适配层预留接入，未来零改造对接。

## 10. 全链路一体化主线（商家视角）

商家需要"内容创作 → 内容分发 → 数据分析 → 投放优化 → 用户运营"一站式打通。五环节功能在 §3 已全覆盖，此处定义**一体化贯通**设计。

**① 全链路主线（顶层导航与数据流）**
```
创作(C/D/E/F/R) → 分发(I/K/B) → 分析(J/M) → 投放优化(S) → 用户运营(U) + 智能客服(AA)
        ↑                                             │
        └──────────── 反馈回路（分析→优化投放→运营用户）┘
```
智享全链运营系统顶层以该主线组织导航，替代纯功能域罗列。

**② 统一归因模型**
- 引入全局 `attribution_id`，`source` 枚举：`content`(内容侧) / `ad`(投放侧) / `user`(用户侧)
- 跨域贯通：C/D/E/F（创作）→ I（分发渠道）→ S（投放花费）→ J（效果）→ U（用户沉淀）
- 任一成交可回溯：选题/脚本 + 投放计划 + 用户来源，同一数据中心

**③ 编排贯通（L 节点扩展）**
- L 工作流节点：`采集 → 分析 → 选题 → 脚本 → 发布 → 复盘 → 投放优化 → 用户运营`
- 支持反馈回路：分析结论自动调整投放策略与运营动作

**④ 商家全链路漏斗（M 增强）**
- 指标视图：内容生产率 → 分发覆盖率 → 投放 ROI → 用户 LTV
- 给商家单一决策视图，而非分散的功能报表

> 功能覆盖完整；一体化依赖上述四点贯通，方满足商家一站式诉求。

## 11. 能力边界（数据来源红线）

**唯一硬约束：不采集用户个人信息。** 全部功能（内容生产、平台对接、视频分发、数据分析、私域运营、达人商单、内容出海等）均保留并建设；区别仅在于**数据来源**——一律经平台开放 API / 用户授权获取，绝不静默抓取个体隐私。

> 用户原意（2026-08-06）："只是不采集个人信息。不是那些功能不做。"——功能全集保留，仅约束数据采集方式。

**① 功能全集（均建设，含此前误判收敛项）**
- **平台对接**：抖音/视频号/小红书/快手 开放平台 API（发布、直播、数据回调）（B/I/K）
- **视频分发**：多平台一键分发、定时发布、挂车、直播推流（I/K）
- **数据分析**：基于平台授权返回数据 + 管理系统商品/订单数据做分析（J/M/D）
- **内容生产**：人性分析/选题/脚本/商品内容，经能力网关 / Skill Gateway（D/E/F/R）
- **复用管理系统能力**：商品（选品/挂车）、订单（归因/分账），接适配层
- **粉丝与私域（U）**：粉丝画像/分层标签/私域承接/推客分销/复购 CRM **全部保留**——数据仅取自平台授权公开/聚合数据
- **达人/商单（V）**：达人档案/商单/分账 **保留**（Could，阶段3）——数据仅取自平台授权
- **内容出海（X）**：TikTok/YouTube/跨境矩阵/AI 译制 **保留**（Could，阶段3）——数据仅取自平台授权

**② 唯一红线（明确不做）**
- 采集**未授权**的个体精准数据：手机号 / 私信原文 / 个体精准地理位置（GPS级） / 个体隐私画像（未公开的兴趣·设备·行为推断）
- 任何静默抓取、第三方个体数据爬取、AI 补全个体隐私
- **明确允许（不视为红线）**：
  - 平台开放 API 返回的**聚合**分布（受众性别/年龄/城市级占比、观众地域分布）
  - 用户**主动授权**披露的信息（主动留资、主动添加企微/微信）
  - 经**订单/交易**归因的买家信息（走管理系统 Order 适配层，授权范围内）
  - 平台返回的**公开**资料（昵称/公开简介/公开作品数）

**③ 数据来源规范**
- 一律经平台开放 API（开放平台/数据开放接口）或用户在智享全链运营系统内主动授权写入
- 平台未公开返回的个人字段：不入库、不推断、不补全
- 各域采集点统一声明数据来源（见 §3 各域"边界"脚注：P/U/V）

> 范围澄清后路线不变（§8）：平台对接 + 内容生产 + 视频分发 + 数据分析 + 私域/达人/出海 全部建设；唯一约束是"不采集用户个人信息"。

## 12. 跨域数据契约（设计决策）

**`attribution_id`（统一归因标识）**
- 原则：**源头生成一次、沿链透传、下游不改写**，保证归因不断裂。
- 格式：`attr_<tenantId>_<bizType>_<hash32>`
  - `bizType` ∈ `content`(短视频) / `live`(直播) / `ad`(投放计划)
  - `hash32`：短哈希(源id + 时间戳 + 租户盐)，全局唯一且不可推测用户
- 生成时机（仅源头）：E 选题创建 → `content`；K 直播建 room → `live`；S 投放建计划 → `ad`
- 透传链（只读透传，禁止重生成）：

| 链路 | 透传字段 |
|---|---|
| 创作链 | E.topics → F.scripts → I.publish_tasks → J.feedback（同 content id）|
| 投放链 | S.ad_campaigns → J（花费归因）|
| 用户链 | U.fans_profiles（记录来源 bizType）|
| 直播复用 | K.live_rooms → H 拆条 → I，派生 `attr_<parent>_clipN` |

- 约束：下游无上游 attribution（手动建内容）允许自建但标 `source=manual`；禁止下游重新生成导致断裂。

**统一响应 envelope**
```
{ code, message, data, trace_id, attribution_id? }
```
- `trace_id`：每请求生成，贯穿 MQ / SSE，排障用
- `attribution_id`：仅写接口（创作/投放/直播/用户沉淀）回包携带，读接口不强制

**实体外键/引用规范**
- 全实体含 `tenant_id`（强隔离）+ `attribution_id`（弱关联，可空）
- 跨域**不建物理外键**（模块解耦），用 `attribution_id` 逻辑关联
- 软删统一 `deleted_at`

## 13. 多租户与隔离（设计决策）

**注入点（三层强制）**
1. JWT Guard 解析 token → `tenant_id / user_id / roles`
2. `TenantContext`（AsyncLocalStorage / request scope）存 tenant_id，请求级
3. TypeORM `TenantSubscriber` 或 `BaseRepository`：所有查询 `where` 自动追加 `tenant_id = :tid`；实体基类 `BeforeInsert` 自动填 tenant_id（防漏）
4. 联通模式：JWT 由管理系统 SSO 签发/校验，`tenant_id` 经 `syncTenant` 对齐（§17 双系统统一账号）

**隔离边界**
| 类型 | 范围 | 规则 |
|---|---|---|
| 强隔离（物理）| accounts / fans_profiles / private_groups / revenue / talents / skill_providers(租户BYO key) / 全部业务数据 | 必须 tenant_id 隔离，跨租户不可见 |
| 弱共享（可选）| human_insights 知识库 | 两层：官方公共模板 + 租户私有派生 |
| 管理系统适配层 | Order/Product/Commission | 经 Auth.syncTenant 对齐，禁跨租户读 |

**个人字段物理不落库（红线工程落地，详见 §11 ②）**
- **字段白名单制**：仅 §4 各域声明字段可入库
- Repository 前置"字段滤除"中间件：命中 `phone / geo / imei / id_card / precise_location / individual_profile` 模式一律剥离
- `fans_profiles` 仅存平台返回的**聚合/公开**字段（粉丝等级、互动聚合），不存私信/手机号
- 越权写入被拦截并记日志（P 合模块可读）

## 14. LLM 输出结构化（设计决策）

**① 输出 JSON Schema（固定枚举，强制 ∈ 字典）**
```json
{
  "top_drivers": ["贪","怕"],
  "top_emotions": ["焦虑","共鸣"],
  "driver_scores": {"贪":0.82,"怕":0.61},
  "emotion_scores": {"焦虑":0.77,"共鸣":0.70},
  "insights": [{
    "category":"价格敏感","driver":"贪","emotion":"焦虑",
    "title":"担心买贵","content":"...","evidence":["c_1","c_2"],"confidence":0.85
  }],
  "model_used":"qwen2.5:7b","prompt_version":"v1"
}
```
- `top_drivers` 必须 ∈ 7 人性字典；`top_emotions` 必须 ∈ 6 情绪字典；否则拒收
- `evidence` 引用原文 comment_id，保证可回溯

**② 校验与降级**
- JSON Schema 强校验；不合法 → 重试一次（换 prompt / 降级本地 Ollama）→ 仍失败转人工，不阻断主流程（发布仍可进行）

**③ 评分校准**
- 强度 0–1 由 LLM 给；用租户标注样本做锚点防虚高
- `confidence < 0.6` 不自动进选题建议（仅人工可见）

**④ 知识库去重**
- `human_insights` 按 `(category, driver, emotion)` 唯一；新洞察 `usage_count++`；历史洞察回灌选题，避免重复造轮（跨租户见 §13 弱共享）

**⑤ Prompt 版本管理**
- 模板入库带 version，workflow.py 平移为 v1，可 A/B 比洞察质量
- 同一模板经能力网关 / Skill Gateway 路由（系统默认 + 租户 BYO，按任务选）

**⑥ 源透明（详见 §2/§4-O）**
- `model_used` 内部记录（含源，用于成本/排障）；**UX 不展示本地/外部**，模型以统一能力呈现

## 15. 统一非功能策略（设计决策）

| 维度 | 统一规则 |
|---|---|
| 限流 | 采集：MQ 令牌桶按 平台+租户 限频（联动 B 账号健康）；发布：按平台日更上限限频；技能调用：并发上限 + 外部配额（text/video/image/voice/digital-human）|
| 重试 | 发布失败指数退避（≤N 次）；`ext_post_id` 幂等去重防重复发；采集 `source_ref+hash` 去重 |
| 降级 | 技能外部失败→本地兜底(Ollama/FFmpeg)→仍失败返回"可重试"不阻断；单平台发布失败不影响其他平台 |
| 可观测 | `trace_id` 贯穿请求/MQ/SSE（§12）；统一日志(tenant,trace,module,action,latency,status)；看板：采集/发布成功率、技能调用量本、降级次数 |

## 17. 双系统统一账号与能力归位（设计决策）

> 前提：智享全链运营系统（电商短视频用户）与智享全链管理系统（实体店）是两层系统，经统一账号打通、数据完全贯通，但功能各有归属。

**① 双模式（integration_mode）**
- `standalone`（独立模式）：未连接管理系统。所有功能自主运营，数据走平台开放 API；库存/订单/商品/财务由运营系统全功能自营。
- `connected`（联通模式）：连接管理系统（统一账号 SSO 登录）。两系统数据完全打通；重叠功能运营系统仅展示，操作归管理系统。
- 切换：`core_integration_cfg.integration_mode`；默认 `standalone`（保"可独立运行"底线），接入管理系统后置 `connected`。

**② 统一账号（SSO）**
- 管理系统为身份提供方（IdP）；运营系统经管理系统 OAuth2/SSO 登录，JWT 由管理系统签发/校验。
- `verifyToken` / `syncTenant` 对齐 tenant_id 与用户；一个账号打通两系统，用户可在两系统间无感跳转。
- standalone 模式运营系统自身账号体系生效；connected 模式统一走管理系统账号（§13 三层注入不变，token 来源切换）。

**③ 数据完全打通**
- 联通模式下 ZhixiangCore 适配层为双向实时通道：订单/库存/商品/财务/租户 与管理系统同步。
- 读：运营系统相关模块经适配层读管理系统数据展示。
- 写：归属管理系统的数据运营系统不直写；操作经 (a) SSO 深链跳管理系统操作页，或 (b) 适配层代理写（如挂车转化自动 `pushOrder` 回管理系统）。
- 管理系统为唯一真源（single source of truth）；运营系统缓存/展示，不反向覆盖。

**④ 功能归位矩阵（联通模式）**
| 功能 | 归属 | 运营系统行为（联通模式）|
|---|---|---|
| 商品主数据（SKU/价格/库存，商品管理）| 管理系统 | 展示（读管理系统）；操作跳管理系统 |
| 库存 / 订单 / 物流打单 | 管理系统 | 展示（读管理系统）；挂车转化推单回管理系统 |
| 财务报表（对账/分账/利润）| 管理系统 | 展示（读管理系统财务）；操作跳管理系统 |
| 商品内容（AI 标题/卖点/话术/种草/详情页，R）| 运营系统 | 自有全功能（在管理系统商品之上增值）|
| 选品决策（T 分析/筛选/榜单）| 运营系统 | 自有全功能 |
| 内容生产/发布/直播/投流/私域/人性分析/工作流/回收/达人/出海/技能 | 运营系统 | 自有全功能 |
| 智能客服（AI 自动回复/工单/转人工，AA）| 运营系统 | 自有全功能（买家咨询/售后/直播评论/私域 DM 自动应答；低置信度转人工工单）|
| 统一标准与管理系统接入（A）| 运营系统持有（接入桥）| standalone 自有账号体系；connected 经管理系统 SSO 登录/同步租户（§17 ②）|
| 能力网关 / Skill Gateway（O）| 运营系统自有 | 全功能（AI/媒体多源路由，不涉双系统归属）|
| 数据模型与基础设施（Q）| 运营系统自有 | 全功能（库表/基建，独立运行即真源）|

> 接入层与基础设施（A/O/Q）为平台级，不参与业务功能归位；其归属如上，独立于双模式切换。

**⑤ 操作路由规则**
- 联通模式：运营系统对"归属管理系统的功能"UI 仅渲染数据 + "去管理系统操作"入口（SSO 透传）；写操作不落地运营系统。
- 独立模式：运营系统自有写逻辑（平台 API / 本地），与现有设计一致。
- 例外：运营系统业务流自然触发的写（如 I 挂车转化生成订单）经适配层 `pushOrder` 推回管理系统，保证管理系统真源。

**⑥ 与现有双源设计的关系**
- 原"双源兜底"（管理系统适配器 / 平台开放 API）升级为：connected→管理系统为真源（展示+推单）；standalone→平台 API 全功能。两套模式由 `integration_mode` 驱动，互不冲突。

## 18. 管理系统侧对接接口规格（联通模式）

> 前提：运营系统通过 ZhixiangCore 适配层对接「智享全链管理系统」（上游 IdP + 数据真源）。本节规定**管理系统侧必须暴露**的接口；运营系统侧适配层调用方见 §7 / 开发顺序设计 A 块 ③。仅 `connected` 模式启用，`standalone` 不调用。

**① 接入配置（运营系统侧）**
- 配置项：`ZHIXIANG_CORE_BASE_URL`（管理系统域名）、`CLIENT_ID`、`CLIENT_SECRET`（OAuth2 confidential）、`CORE_JWT_PUBLIC_KEY`（验签）或共享密钥
- 开关：`core_integration_cfg.integration_mode=connected` 触发；默认 `standalone`（保可独立运行）
- 网络：运营系统→管理系统 出网限白名单域名；TLS 1.2+

**② 统一账号 SSO（OAuth2 Authorization Code + JWT）**
- 授权：`GET {BASE}/oauth/authorize?client_id&redirect_uri&scope=openid tenant&state` → 管理系统登录/授权页
- 换码：`POST {BASE}/oauth/token`（grant_type=authorization_code）→ `access_token`(JWT) / `refresh_token` / `expires_in`
- 校验：`POST {BASE}/api/verifyToken`（携带 JWT）→ `{tenant_id, user_id, roles, expire_at}`；运营系统亦可本地用 `CORE_JWT_PUBLIC_KEY` 验签（不联网）
- 租户同步：`POST {BASE}/api/syncTenant`（tenant_id / 店铺列表 / 账号映射）→ 运营系统对齐 tenant_id 与账号
- 账号列表：`GET {BASE}/api/accounts`（管理系统侧子账号/店铺，供运营系统 B 账号矩阵映射）
- JWT claims：`tenant_id, user_id, roles[运营/财务/仓配…], exp, iss=智享全链管理系统`；运营系统 TenantContext 直接消费

**③ 商品主数据（Product，只读展示）**
- `GET {BASE}/api/products?page&pageSize&sku&category&status` → `{page,pageSize,total,list:[{sku,title,price,stock,status,category,images,updated_at}]}`
- `GET {BASE}/api/products/:sku` → 单品详情
- 运营系统 R 商品内容中心叠加 AI 生成内容（标题/卖点/详情页）于展示层，不写回管理系统

**④ 订单与库存（Order / Inventory）**
- 读：`GET {BASE}/api/orders?page&pageSize&platform&status&begin&end`；`GET {BASE}/api/orders/:order_id`；`GET {BASE}/api/orders/:order_id/logistics`
- 写（仅自然触发）：`POST {BASE}/api/orders`（挂车转化 `pushOrder` 回推；body 含 `attribution_id` / `platform` / `product_sku` / `amount` / `buyer_聚合(加密)`）；幂等键 `order_id` 由运营系统生成
- 库存：`GET {BASE}/api/inventory?sku`；库存真源在管理系统，运营系统只读
- 回调（管理系统→运营系统）：`POST {BASE}/core/callback/order-settled`、`/stock-updated`（Webhook，见 ⑦）

**⑤ 财务与分账（Commission / Finance）**
- 读：`GET {BASE}/api/commission?begin&end&status`；`GET {BASE}/api/financial?type=对账|利润|报表`
- 写：`POST {BASE}/api/settlement`（settleCommission 回写分账结果；运营系统 W 对账后回推）
- 回调：`POST {BASE}/core/callback/financial-updated`

**⑥ 租户变更回调**
- `POST {BASE}/core/callback/tenant-updated`（管理系统租户/账号变更 → 运营系统重同步）

**⑦ 通用契约（双方一致）**
- 鉴权：管理系统 API 一律 `Authorization: Bearer <JWT>`（管理系统签发）；Webhook 用 `X-Core-Signature = HMAC-SHA256(body, CLIENT_SECRET)` 校验来源
- 响应体：`{code, message, data, trace_id}`（与运营系统统一响应体一致）
- 分页：`{page, pageSize, total, list}`；时间 `ISO8601`
- 幂等：写接口以业务键去重（`order_id` / `settlement_id`）
- 安全：买家/收货等敏感字段由管理系统侧加密或脱敏后传输；运营系统仅存密文/聚合
- 限流：管理系统侧按 `client_id` 限流；运营系统侧超时 5s + 退避重试

**⑧ 与 §7 / §17 的对应**
- 本节 = 管理系统侧**被调用方**契约；§7 = 运营系统适配层**调用方**接口（`ssoLogin/verifyToken/syncTenant/listAccounts`、`listProducts/getProduct`、`queryOrder/queryStock/pushOrder`、`queryCommission/queryFinancial/settleCommission`、四类 callback）；二者一一对应
- 联通模式启用后，Y/R/W 在运营系统仅展示（读 ③④⑤），写经 SSO 深链或 `pushOrder`/`settlement` 回推（§17 ④⑤）；管理系统唯一真源
