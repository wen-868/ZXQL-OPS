# 运营系统 ↔ 管理系统 一致性规范（CONSISTENCY）

> 目的：新建「智享全链运营系统」必须与现有「智享全链管理系统（ZXQL-MS）」保持工程一致。
> 管理系统代码位置：`D:\Users\ZXQL\ZXQL-MS\wen-ssystem\backend`
> - 主系统：`src/` —— Express 5 + TypeScript（业务逻辑、响应封装、鉴权、错误处理的标准来源）
> - AI 基座：`ai-base/` —— NestJS 11 + TypeORM + MySQL（新模块，注释明确"与项目统一标准对齐"）
>
> 运营系统规划为 NestJS，因此**以 `ai-base` 为代码底座**，并**吸收 `src/` 的业务约定**（响应格式、错误码、多租户字段、env 变量名）。

## 1. 技术栈对齐

| 项 | 管理系统做法 | 运营系统对齐 |
|---|---|---|
| 语言/运行时 | TypeScript + Node (ESM) | 同 |
| 框架 | 主系统 Express；新模块 NestJS 11 | **NestJS 11**（`@nestjs/core` 等，跟随 `ai-base` 版本） |
| ORM | `ai-base` 用 **TypeORM** | **TypeORM** |
| 数据库 | **MySQL**（`env.DB_NAME` 默认 `liquor_inventory`） | **MySQL**（独立库，规划 §17 要求独立部署/独立库/独立进程） |
| 校验 | 主系统 `zod`；NestJS 侧用 `class-validator` | **`class-validator` + `class-transformer`**（NestJS 惯例，全局 `ValidationPipe`） |
| 日志 | `pino`（`LOG_LEVEL`） | **`pino`/`nestjs-pino`** |
| 限流 | `express-rate-limit` + 可选 RedisStore | 等价（NestJS 可用 `@nestjs/throttler` 或复用逻辑） |
| CSRF | `csrfMiddleware`（所有状态变更路由默认开启） | 同，对所有写接口开启 |
| 进程管理 | `tsx watch` / `tsx` + ESM | 同 |

## 2. 统一响应封装（**最重要，强制一致**）

来源：`backend/src/shared/response.ts`（`ok` / `err`）。

```ts
// 成功
ok({ data, msg?, req? })        // → { code: "0", msg, data, traceId }

// 失败
err(errorCode, message, data?)  // → { code: <错误码字符串>, msg: message, data, traceId }
```

- 字段顺序固定：**`code` → `msg` → `data` → `traceId`**（注意用 `msg`，非 `message`）。
- `code: "0"` 表示成功；业务/系统错误用**字符串错误码**（见 §3）。
- `traceId`：每次请求唯一，贯穿日志，便于排障。

> ⚠️ 待统一点：`ai-base` 内 `error-code.ts` 用了 `message` 字段；新建运营系统**统一用 `msg`**，与 `src/shared/response.ts` 主约定保持一致。在 NestJS 侧通过 `ResponseInterceptor` + `AllExceptionsFilter` 落地该信封。

**NestJS 落地方式**：
- `ResponseInterceptor`：把控制器返回值包成 `{ code:"0", msg, data, traceId }`。
- `AllExceptionsFilter`：捕获 `AppError` / `HttpException`，输出 `{ code, msg, data, traceId }`。

## 3. 错误处理与错误码

来源：`backend/src/shared/app-error.ts` + `error-code.ts` + `middleware/error-handler.ts`。

- 错误码为**字符串 key**（如 `"USER_NOT_FOUND"`、`"INVALID_PARAM"`、`"AUTH_TOKEN_EXPIRED"`）。
- `err(key, message, data?)` 工厂：用 key 查 `error-code.ts` 取默认 message，可被传入 message 覆盖。
- `AppError extends Error`：携带 `code` / `httpStatus` / `data`。

**运营系统对齐**：
- 复用同一套 `error-code.ts` 的码表风格（字符串 key + 默认文案 + HTTP 状态）。
- 新建运营系统专属错误码时，沿用 `{ key, message, data? }` 结构。
- `AllExceptionsFilter` 输出 `{ code, msg, data, traceId }`，与 `err()` 完全同构。

## 4. 多租户（**核心，强制一致**）

来源：`ai-base/src/tenant/`（Tenanter 模块、TenantContext、tenant.middleware）。

- 实体基类带 **`tenantId`** 列（租户隔离字段），所有业务表必须有。
- 租户标识从请求头 **`tenantId`** 获取，存进 `TenantContext`（AsyncLocalStorage / 请求作用域）。
- 仓库/服务层自动按 `tenantId` 过滤，**不靠物理外键跨域关联**。

**运营系统对齐**：
- 新建所有 entity 继承同一 `BaseEntity`（`id` / `tenantId` / `createdAt` / `updatedAt` / `deletedAt` 软删）。
- `attribution_id`（`attr_<tenant>_<type>_<hash32>`，规划 §核心）**源头生成一次、沿链只读透传**，不与 tenantId 冲突，二者并存。
- `tenant.middleware` 模式照搬：解析 `tenantId` 头 → 写入 `TenantContext`。

## 5. 鉴权

来源：`backend/src/middleware/auth.ts`（requireAuth / requireAuthWithTenant / requirePlatformAuth）。

- JWT 校验，`JWT_SECRET` 签名。
- `AuthUser` 形状（建议对齐）：`{ id, tenantId, role, type, ... }`（`type` 区分 admin/saas/merchant/platform）。
- 路由 auth 模式三档：
  - `requireAuthWithTenant`（默认）：认证 + 租户隔离 + CSRF
  - `requireAuth`：仅认证 + CSRF
  - `requirePlatformAuth`：平台总后台 + CSRF

**运营系统对齐（NestJS）**：
- 等价 Guard：`JwtAuthGuard` + `TenantGuard`；用 `@AuthUser()` 装饰器取当前用户。
- 规划 §17「双模式」：`standalone` 全功能自营；`connected` 经 SSO 打通管理系统。第一版先 `standalone`，但 `AuthUser.type` 预留 `connected` 分支。

## 6. 配置管理（env 变量名强制一致）

来源：`backend/src/config/env.ts`（集中入口，`src/shared/env.ts` 仅 re-export）。

运营系统 `.env` / `env.ts` **复用同名变量**，避免双系统部署时认知分裂：

```
PORT / NODE_ENV
JWT_SECRET            # 必填，缺失启动失败
CSRF_SECRET           # 缺省回退 JWT_SECRET
DB_HOST / DB_PORT / DB_USER / DB_PASSWORD / DB_NAME
DB_CONNECTION_LIMIT / DB_MAX_IDLE / DB_IDLE_TIMEOUT / DB_QUEUE_LIMIT / DB_ACQUIRE_TIMEOUT
REDIS_HOST / REDIS_PORT / REDIS_URL
DOMAIN / API_DOMAIN / ADMIN_DOMAIN / MERCHANT_DOMAIN
LOG_LEVEL / CORS_ORIGINS
FEISHU_WEBHOOK_URL / FEISHU_ALERT_WEBHOOK_URL
WECHAT_* / WX_* / JPUSH_* / FCM_* / HMS_*   # 按需启用
```

> 新增运营系统专属变量时，加 `OPS_` 前缀（如 `OPS_OLLAMA_HOST`、`OPS_LLM_GATEWAY`），与管理系统变量区分又保持集中管理风格。

## 7. 数据库与实体约定

来源：`ai-base/src/database/`（TypeOrmModule + 多数据库）+ 实体基类。

- TypeORM `BaseEntity`：`id`(主键) / `tenantId` / `createdAt` / `updatedAt` / `deletedAt`(软删)。
- 时间字段类型统一（建议 `datetime`）。
- 分页：列表接口统一返回 `{ list, total, page, pageSize }`（与 `src` 约定对齐）。

**运营系统对齐**：
- 数据库 module 结构照搬 `ai-base/src/database/`（`DatabaseModule.forRoot`、多库配置）。
- 能力网关（`O` 模块）要能接 **本地 Ollama（qwen2.5:7b）**，配置走 `OPS_OLLAMA_*` / `OPS_LLM_GATEWAY`。
- 素材/成片/直播录屏走对象存储（MinIO 或云 OSS），配置沿用集中 `env.ts` 风格。

## 10. 待解决的一致性问题（需你拍板）

1. **响应字段名**：主系统用 `msg`，`ai-base` 错误码用 `message` → 运营系统**统一 `msg`**（推荐）。
2. **校验库**：NestJS 侧用 `class-validator`（与 `ai-base` 一致）还是强行对齐主系统 `zod`？→ 推荐 `class-validator`。
3. **数据库库名**：规划要求独立库（如 `zhixiang_ops`），不与 `liquor_inventory` 混用 → 确认库名。
4. **双系统账号归位（§17）**：第一版是否连 `ZhixiangCore` SSO？→ 先 `standalone`，`AuthUser.type` 预留。
5. **CSRF**：管理系统的 CSRF 依赖 cookie+token，运营系统若用同域 SSO 需复用同一套 `CSRF_SECRET`。
