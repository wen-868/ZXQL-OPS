# 智享全链运营系统 · 模块化开发步骤设计

> 本文只设计**开发顺序与细分步骤**，不涉及编码。
> 原则：**脚手架优先 → 按数据依赖链逐模块 → 单模块设计+开发+自测完善后再下一个**。
> 每个模块细分为可执行的开发步骤，并附接口契约与验收标准。

---

## 1. 推进原则

| 原则 | 说明 |
|---|---|
| 脚手架优先 | core/integration/skill/config/db 先成型，业务模块不重复造轮子 |
| 依赖链驱动 | 按数据流向排顺序，上游先完善，下游才能联调 |
| 单模块闭环 | 每模块：设计 → 建实体 → 建服务 → 建控制器 → 自测 → 联调上下游 → 确认完善 |
| 价值优先 | 阶段1 跑通短视频闭环，阶段2 补商业化，阶段3 增强 |

---

## 2. 模块依赖关系（数据流向）

```
B 账号矩阵 ─accounts─▶ I 发布（多账号分发）
C 情报采集 ─comments─▶ D 人性分析 ─insights─▶ E 选题 ─topics─▶ F 脚本 ─scripts─▶ I 发布 ─published─▶ J 回收
                                                                        ▲ L 编排串联 B→C→D→E→F→I
        J 回收 ──回流──▶ D（再分析闭环）         S 投放 / U 用户 经 attribution_id 贯通全链
        I/S 挂车转化 ─▶ Y 订单物流（履约）─▶ W 对账（佣金）；Y 经 attribution_id 贯通全链
```

---

## 3. 模块化推进总顺序

```
第0步 脚手架(基建)
  └─ 第1步 B 账号矩阵(core) → 第2步 C 情报采集 → 第3步 D 人性分析 → 第4步 E 选题 → 第5步 F 脚本
        → 第6步 I 发布 → 第7步 L 编排 → 第8步 J 回收
阶段2 商业化：B-advanced(环境隔离/防关联) + T 选品 → R 商品内容 → K 直播 → S 投流 → U 私域 → W 对账 → Y 订单物流 → AA 智能客服(售后/咨询) → M 决策
阶段3 增强：G 素材 → H 成片 → N 权限 → V 达人 → X 内容出海
```

## 4. 模块化细分开发步骤

> 每模块步骤标注类型：[设]设计 [实]实现 [测]自测 [联]联调

### 第0步 脚手架（工程基座，非业务）

- **[设] 目录结构**：`src/{core,config,database,integration,skill,health}` + 各业务模块目录占位
- **[实] config**：环境变量模块（DB/Redis/MQ/MinIO/Ollama/外部模型/feature flag），`.env.example`
- **[实] database 连接**：TypeORM 配置 + MySQL 连接（表 / Migration / 实体基类见 Q 详细设计）
- **[实] health 示例模块**：验证工程可启动、统一响应体生效
- **[实] UI 基座**：设计系统（组件/主题/规范）、整体布局框架、基于全链路主线（总体规划 §10）的导航骨架——**层1 UI 在此步完成，不依赖业务数据**
- **[测]** 启动工程；UI 基座可渲染导航骨架
- **[联]** 无（基建）；输出：标准基座供后续模块直接使用

> A（统一标准与管理系统接入）、O（能力网关 / Skill Gateway）、Q（数据模型与基础设施）的详细设计见下方各自独立 7-block 块；Z（技能中心）详见 §4-Z 及本步 ④。

**详细设计（贯彻 §11–§16）**

**① 工程结构（NestJS 模块化）**
- 目录：`core / config / database / integration / skill / health` + 业务模块占位
- 配套：`docker-compose`（MySQL/Redis/RabbitMQ/ES/MinIO）单台部署；`nest-cli.json`/`tsconfig`/`ormconfig`

**② UI 基座（层1，§10）**
- 设计系统（组件/主题/规范）+ 整体布局 + 全链路主线（创作→分发→分析→投放→用户）导航骨架；不依赖业务数据

**③ 脚手架总验收标准（§7）**
- [ ] 工程启动；envelope 含 trace_id；异常过滤器不泄露栈
- [ ] UI 基座可渲染导航骨架
- [ ] docker-compose 单台起全部基础设施
- [ ] A/O/Q/Z 各自详细设计验收通过（见其块）

**④ Z 技能中心 详细设计（§4-Z，管理平面）**
- `skills`(type, builtin, enabled) 系统内置技能目录（text/video/image/voice/digital-human）；`skill_installs`(tenant_id, skill_id, provider_id, enabled) 租户启用/绑定 BYO provider
- 管理 UI：技能市场(列出 5 类内置技能) → 租户启用 → 选/配 Provider（系统默认 or 自建 BYO）
- 与 O 网关联动：Z 决定"装什么/用哪个源"，网关负责路由+降级+源透明
- 验收：租户可启用技能、可配置自有 Provider；未启用技能不在智享全链运营系统暴露

### A. 统一标准与管理系统接入 · 详细设计 [Must·脚手架]

**① 边界与合规（§11/§13/§17）**
- 多租户强隔离（§13）：tenant_id 贯穿所有查询；跨租户不可见
- 双模式（§17）：仅经 ZhixiangCore 适配层访问管理系统，禁直连；适配层默认 stub（feature flag off）
- 密钥/Token 加密存储；JWT 由管理系统（connected）或运营系统（standalone）签发，不混用

**② 数据模型（TypeORM，§6/§13）**
| 实体 | 核心字段 |
|---|---|
| core_integration_cfg | tenant_id, enabled, base_url, integration_mode(standalone/connected), feature_flags(JSON) |
| base.entity（基类） | id, tenant_id, created_at, updated_at, deleted_at(软删)；BeforeInsert 自动填 tenant_id |

**③ 接口契约**
- core 标准层：响应拦截器 统一 `{code,message,data,trace_id,attribution_id?}`；JWT Guard → TenantContext(AsyncLocalStorage) → `tenant.subscriber` 自动 append `tenant_id`
- integration 适配层接口：Auth(SSO) `ssoLogin/verifyToken/syncTenant/listAccounts`；Product `listProducts/getProduct`；Order·Inventory `queryOrder/queryStock/pushOrder`；Commission·Finance `queryCommission/queryFinancial/settleCommission`
- callback：`POST /core/callback/order-settled`、`/stock-updated`、`/tenant-updated`、`/financial-updated`
- 管理系统侧需暴露的具体端点（authorize/token/verifyToken/syncTenant/accounts、products、orders/inventory、commission/financial、四类 callback）与 Webhook 签名校验，见总体规划 §18

**④ 服务逻辑**
- tenant_id 注入/读取：JWT → TenantContext → Subscriber 自动带参（强隔离工程实现）
- 独立运行：运营系统自有账号体系（standalone）
- 连通模式：管理系统 SSO 登录 → `verifyToken` → `syncTenant` 对齐租户/用户；切换 `integration_mode=connected`
- 业务模块仅经适配层接口调用管理系统，不感知 stub/真实实现

**⑤ 联动契约**
- → 所有业务模块：提供 tenant_id 隔离 + 统一响应体（基类/base.entity）
- → Y/R/W：联通模式读管理系统（功能归位，§17 ④）
- → O/Z：提供账号/租户上下文
- ← 管理系统：SSO 登录 / 四类回调通知

**⑥ 验收标准（§7）**
- [ ] 工程启动；envelope 含 trace_id；异常过滤器不泄露栈
- [ ] JWT + TenantContext + subscriber 生效（查询自动带 tenant_id，跨租户不可见）
- [ ] 适配层 stub 编译通过，业务可经接口调用
- [ ] 双模式 standalone/connected 可切换；connected 经 SSO 登录/同步租户
- [ ] callback.controller 收四类管理系统通知

**⑦ UI（层1，§10）**
- 无独立页面；登录态/租户上下文由 UI 基座提供；连通模式登录入口在登录页（SSO 跳转）

### O. 能力网关 / Skill Gateway · 详细设计 [Must·脚手架]

**① 边界与合规（§11/§2/§4-O）**
- API Key 加密、不返前端；按 tenant_id 隔离（租户 BYO 仅本人可见，不跨租户共享）
- 源对 UX 透明：不标注"本地/外部"，model_used/source 仅内部记（溯源）
- 不采集用户个人信息；仅经平台授权/用户授权数据驱动生成

**② 数据模型（TypeORM，§6）**
| 实体 | 核心字段 |
|---|---|
| skill_providers | tenant_id, type(text/video/image/voice/digital-human), name, api_key(加密), models, enabled |
| skill_usage_logs | tenant_id, skill_id, provider_id, model, tokens, cost, latency, created_at |

**③ 接口契约**
- `skill.interface.invoke(skill, payload)→{content, model_used, source}`；技能类型 text-generate / video-generate / image-generate / voice-clone / digital-human
- `provider.interface.generate(payload)→{content, model_used}`
- `skill.gateway.route(skill, task)`：按技能+任务/配置选 provider → 外部失败降级本地 → 仍失败返"可重试"

**④ 服务逻辑**
- 路由：按技能类型 + 任务 + 租户配置选 provider（本地 Ollama 默认 / 外部 / 租户 BYO）
- 降级：外部失败→本地；仍失败返"可重试"（不阻断业务）
- 用量成本日志（按租户/技能/模型）；BYO provider 从 skill_providers 按 tenant 读

**⑤ 联动契约**
- ← D/E/F/R/G/H/K/X/Z：能力消费者（text/video/image/voice/digital-human 经本网关，源透明）
- → 记录 model_used/source（内部溯源，不暴露终端用户）
- → Z 技能中心：Z 决定"装什么/用哪个源"，网关负责路由+降级

**⑥ 验收标准（§7）**
- [ ] 走本地 Ollama 跑通文本生成；外部可配
- [ ] 降级单测通过（外部失败→本地→可重试）
- [ ] 租户 BYO 隔离（仅本人可见自有 key）；用量日志落库
- [ ] API Key 加密、不返前端

**⑦ UI（层2，§10）**
- 无独立 UI；管理平面在 Z 技能中心（市场/启用/Provider 配置）

### Q. 数据模型与基础设施 · 详细设计 [Must·脚手架]

**① 边界与合规（§11/§13）**
- 数据按 tenant_id 隔离；统一软删（deleted_at）；敏感字段加密（见各域 §11 ②，如订单 buyer_聚合、客服 buyer_ref）
- 基础设施单台可部署；业务平台 API 之外不强制出网

**② 数据模型（TypeORM，§6）**
- 核心表见 §6：accounts / competitors / analysis_tasks / topics / scripts / materials / videos / publish_tasks / workflow_defs / live_rooms / products / selection_products / ad_accounts / fans_profiles / revenue_records / orders / logistics_tracks / waybills / talents / skill_providers / skills / skill_installs / core_integration_cfg / cs_sessions / cs_messages / cs_knowledge / cs_tickets / cs_settings
- 统一实体基类 base.entity（id/tenant_id/时间戳/软删；BeforeInsert 自动填 tenant_id）
- 索引策略：tenant_id + 业务键（如 order_id / product_id / session_id）；联合索引避免全表扫

**③ 接口契约**
- database 模块：TypeORM config + MySQL 连接；统一实体基类；Migration 接口
- 基础设施连接：Redis（缓存/限流/去重）· RabbitMQ（异步事件）· ES（检索）· MinIO（媒资存储，前端预签名 URL）

**④ 服务逻辑**
- Migration 与索引：按 §6 表结构生成 Migration；base.entity 软删/tenant_id 自动填
- 基础设施接入：Redis 缓存/限流/去重；RabbitMQ 异步（I/K/U→客服等事件驱动）；ES 检索；MinIO 媒资（直播录屏→拆条）
- 单台部署：docker-compose（MySQL/Redis/RabbitMQ/ES/MinIO）

**⑤ 联动契约**
- 被所有业务模块依赖：提供表结构 / Migration / 实体基类 / 基础设施连接
- → 各域数据模型（§6）落库；tenant_id 隔离贯穿

**⑥ 验收标准（§7）**
- [ ] Migration 通过；base.entity 软删/tenant_id 自动填
- [ ] 基础设施连接就绪（Redis/RabbitMQ/ES/MinIO）
- [ ] 索引生效（tenant_id + 业务键）；敏感字段加密落库

**⑦ UI**
- 无（基础设施层）

### 第1步 B 账号矩阵(core) [Should·阶段1]

> B-core 提前至阶段1（脚手架后、I 前），使 I 多账号自动分发在阶段1 即可用；B-advanced（环境隔离/防关联）留阶段2。

- **[设] 实体**：`accounts`(tenant_id, platform, platform_account_id, name, persona, auth_token(加密), refresh_token(加密), token_expire_at, health_score, status, group_id)、`account_groups`(tenant_id, name)、`account_health_logs`(tenant_id, account_id, metric, value, logged_at)
- **[设] 接口契约**：OAuth 接入（供 I/K/U 读取多账号）；Token 续期；矩阵看板
- **[实] service**：多平台 OAuth2 接入（抖音/视频号/小红书/快手，L1 开放 API）；token AES 加密存储 + 定时 refresh 续期；健康监控（定时拉限流/违规/权重 → account_health_logs，超阈值告警）；分组/人设档案；矩阵看板聚合
- **[实] controller**：`POST /accounts/oauth/start`、`GET /accounts/oauth/callback`、`GET /accounts`、`POST /accounts/:id/refresh`、`POST /account-groups`、`GET /accounts/matrix`
- **[测]** OAuth 流程跑通；token 加密落库；refresh 自动；健康监控写入
- **[联]** 供 I（多账号分发）/ K（矩阵直播）/ U（多账号私域）读取 accounts
- **验收**：OAuth 接入+加密+续期；健康监控；I 可多账号分发（联动 I 详细设计）

**详细设计（贯彻 §11–§16）**

**① 边界与合规（§11）**
- 账号接入走平台开放 API OAuth（L1），不抓取个人隐私；账号元数据(platform/name/persona) 存，不存个人字段
- 防关联（B-advanced）：账号环境隔离（指纹/IP/设备）留阶段2

**② 数据模型（TypeORM，§13）**
| 实体 | 核心字段 |
|---|---|
| accounts | tenant_id, platform, platform_account_id, name, persona, auth_token(加密AES), refresh_token(加密), token_expire_at, health_score, status, group_id |
| account_groups | tenant_id, name, description |
| account_health_logs | tenant_id, account_id, metric(限流/违规/权重), value, logged_at |
> 统一基类（§13）；auth_token/refresh_token 加密不返前端

**③ 接口契约（REST，envelope 见 §12）**
| 方法 | 路径 | 说明 |
|---|---|---|
| POST | /accounts/oauth/start | 发起 OAuth（platform）|
| GET | /accounts/oauth/callback | 平台回调，存 token(加密) |
| GET | /accounts | 账号列表（分组/健康）|
| POST | /accounts/:id/refresh | Token 续期 |
| POST | /account-groups | 建分组 |
| GET | /accounts/matrix | 矩阵看板（健康/权重概览）|

**④ 服务逻辑**
- OAuth 适配：各平台 OAuth2，token 加密（AES）存储；refresh 定时任务自动续期
- 健康监控：定时拉平台账号状态（限流/违规/权重）→ account_health_logs；超阈值告警
- 矩阵看板：聚合健康/权重前端展示
- 防关联（advanced，阶段2）：账号环境隔离（指纹/IP/设备绑定）、防关联封号评估

**⑤ 消费契约（供 I/K/U）**
- I 发布：读 accounts 列表，按分组/平台多选分发
- K 直播：读 accounts 做矩阵直播
- U 私域：按 account 维度承接

**⑥ 验收标准（§7）**
- [ ] accounts/group/health 建表+Migration
- [ ] OAuth 跑通，token 加密存储，refresh 自动
- [ ] 健康监控定时拉取+告警
- [ ] I 能读 accounts 多账号分发（联动 I）
- [ ] 无个人隐私字段入库

**⑦ UI（层2，§10）**
账号列表/OAuth 绑定/分组/矩阵看板/健康告警

### 第2步 C 市场情报与竞品采集 [Must·阶段1]

- **[设] 实体**：`competitors`(platform/name/url/category/monitor_enabled)、`collected_comments`(source_type/source_ref/content/author_id(公开ID)/likes/is_clean)
- **[设] 接口契约**：输出 `collected_comments`（供 D 消费）；采集任务异步
- **[实] service**：竞品监控、爆款采集、评论抓取（HTTP 爬虫/平台 API，限频）、热点追踪；采集任务入 RabbitMQ 异步执行；数据清洗（去重/去广告/归一）
- **[实] controller**：`POST /competitors`、`POST /collect`、`GET /collect/:id`（进度）
- **[测]** 单测采集落库；验证 comments 可被 D 读取的结构
- **[联]** 供 D 消费 `collected_comments`（下一模块）
- **验收**：能采集并落库评论；契约稳定

**详细设计（贯彻 §11–§16）**

**① 合规边界**
- 采集方式矩阵：L1 开放 API 优先（抖音/视频号/小红书/快手 开放平台）；L2 授权爬虫仅公开页；L3 禁个体隐私（§11 ②）
- 字段白名单：`collected_comments` 仅存 `content / author_id(平台公开ID) / likes / platform / source_ref / collected_at`；命中 `phone/geo/imei/individual_profile` 一律剥离并记日志（§13）
- 审计：每次采集写 `collect_tasks.source_level / scope / fields_collected`，P 可读（§11 ③）
- 无 attribution_id：C 为公开情报，仅 tenant_id 隔离；attribution_id 从 E 开始（§12）

**② 数据模型（TypeORM）**
| 实体 | 核心字段 |
|---|---|
| competitors | tenant_id, platform, name, url, category, monitor_enabled, last_collected_at, health |
| collected_comments | tenant_id, source_type(comment/video/meta), source_ref, platform, content, author_id(公开ID), likes, is_clean, clean_result, collected_at |
| collect_tasks | tenant_id, type(monitor/hot/comment/keyword), target, platform, status(pending/running/done/failed), progress, source_level(L1/L2), scope, fields_collected(JSON), error_msg |
| hot_snapshots | tenant_id, platform, hot_type, title, heat, url, captured_at |
> 统一基类：id/tenant_id/时间戳/软删（§13）

**③ 接口契约（REST，envelope 见 §12）**
| 方法 | 路径 | 说明 | 产出 |
|---|---|---|---|
| POST | /competitors | 新增竞品/对标账号 | competitor |
| POST | /competitors/:id/monitor | 开启/关闭监控 | monitor_enabled |
| POST | /collect | 发起采集任务{type,target,platform,source_level,scope} | {task_id, trace_id} |
| GET | /collect/:id | 任务进度 | {status,progress,collected_count} |
| GET | /collected-comments | 供 D 消费(分页/clean) | collected_comments[] |
| POST | /keywords/mine | 关键词挖掘 | hot_words[] |
| GET | /hot | 热点榜 | hot_snapshots[] |

**④ 服务逻辑**

### 第7步 L 工作流编排 [Must·阶段1]

- **[设] 实体**：`workflow_defs`(name/nodes/edges/trigger/cron_expr/enabled/tenant_id)、`workflow_runs`(def_id/status/progress/started_at/finished_at)、`workflow_run_logs`(run_id/node/status/input/output/ts/trace_id)

- **[实] service**：节点类型（采集/分析/选题/脚本/发布/回收）；触发（手动/Cron/事件）；MQ 异步执行（单节点失败隔离，不影响其余节点）；SSE 实时进度；条件分支（爆款追投：数据达标自动派生选题）；DAG 校验（环检测/必填入参）
- **[实] controller**：`POST /workflows`、`POST /workflows/:id/run`、`GET /workflow-runs/:id/stream`(SSE)、`GET /workflows`、`POST /workflows/:id`
- **[测]** 一键跑通 C-D-E-F-I 闭环；SSE 可见进度；单节点失败隔离；条件分支触发
- **[联]** 串联阶段1 全部模块（C/D/E/F/I）+ 反馈至 J（回收）/D（再分析）
- **验收**：闭环可编排运行；SSE 进度可视；节点失败隔离

**详细设计（贯彻 §11–§16）**

**① 边界与合规（§11）**
- 编排仅调度既有模块，不新增数据采集；各节点沿用上游模块合规边界（C 公开评论、I 平台 API 等）
- trace_id 贯穿 MQ/SSE（§12），排障可定位到具体节点

**② 数据模型（TypeORM，§12/§13）**
| 实体 | 核心字段 |
|---|---|
| workflow_defs | tenant_id, name, nodes(JSON: {id,type,config,deps}), edges(JSON: {from,to,condition?}), trigger(manual/cron/event), cron_expr, enabled, created_at |
| workflow_runs | tenant_id, def_id, status(queued/running/success/failed/partial), progress, started_at, finished_at |
| workflow_run_logs | tenant_id, run_id, node_id, status(running/done/failed/skipped), input(JSON), output(JSON), ts, trace_id |
> 统一基类（§13）；nodes.type ∈ {collect,analyze,ideate,script,publish,recycle}；edges 支持 condition（条件分支）；trace_id 每节点记录（§12 可观测）

**③ 接口契约（REST + SSE，envelope 见 §12）**
| 方法 | 路径 | 说明 | 产出 |
|---|---|---|---|
| POST | /workflows | 新建/保存编排(nodes/edges/trigger) | workflow_defs |
| GET | /workflows | 编排列表 | workflow_defs[] |
| POST | /workflows/:id | 启停/更新编排 | workflow_defs |
| POST | /workflows/:id/run | 触发运行(手动/事件) | {run_id, trace_id} |
| GET | /workflow-runs/:id/stream | SSE 实时进度(节点状态/日志) | SSE 流 |

**④ 服务逻辑**
- 节点编排：每个节点 = 对上游模块的调用封装（collect→C, analyze→D, ideate→E, script→F, publish→I, recycle→J）；节点产出经 attribution_id 沿链透传（§12）
- 异步执行：run 拆为节点任务入 RabbitMQ；每个节点独立消费、独立失败隔离（单节点 failed 标记 + 记日志，不阻断其他节点；整 run=partial 而非全败）
- SSE 进度：`workflow_runs.progress` + `workflow_run_logs` 实时推送（每节点 done/failed 触发事件）
- 条件分支：edges.condition 支持数据阈值（如 J 回收播放量≥X → 自动派生追投选题进 E），实现"爆款追投"
- DAG 校验：保存时环检测 + 节点必填入参校验，避免无效编排
- 反馈回路：recycle 节点(J) 结论 → 自动调整 E 选题权重 / F 钩子情绪（落实 §10 一体化反馈回路）

**⑤ 消费契约（贯通全链，§6/§12）**
- 串联 C→D→E→F→I 为自动 pipeline；recycle(J) 回流 D 再分析闭环
- attribution_id 在 E 生成后沿节点透传至 I→J，编排层不重生成（§12）

**⑥ 验收标准（§7）**
- [ ] workflow_defs/runs/logs 建表+Migration
- [ ] 一键跑通 C-D-E-F-I 闭环；SSE 实时进度可见
- [ ] 单节点失败隔离（整 run=partial，其余节点完成）；DAG 环检测生效
- [ ] 条件分支触发（爆款追投）；反馈回路（回收→调整 E/F）可用
- [ ] 与 C/D/E/F/I 全部联通；trace_id 贯穿排障

**⑦ UI（层2，§10）**

## 5. 流程完善（行业 SOP 固化，来自竞品分析）

**短视频工业化六步法（标准流程）**
```
选题策划 → 脚本撰写 → 画面生成 → 剪辑合成 → 发布分发 → 数据复盘
   C/D         E/F         G          H         I/S        J/M
```
- 每一步对应模块明确；画面生成(G)、剪辑合成(H) 在阶段3；发布(I) 与投流(S) 在阶段2 联动

**直播全流程 SOP**
```
准备(选品T/脚本R/素材K/私域宣发U/商品审核) → 开播 → 中控(商品/福袋/互动/AI代播) → 结束 → AI复盘(K/J)
```
- 准备环节显式纳入 U 私域宣发物料；中控含 AI 代播接管、库存预警、预设弹窗

**合规风控 SOP（独立显式）**
```
选题合规(P) → 脚本合规校验(F) → 发布前预检(I/P) → 直播违禁词实时监测(K/P) → 违规处置复盘(J)
```

**行业七大模块 SOP → 智享全链运营系统映射**
| 行业 SOP | 对应域 | 落地动作 |
|---|---|---|
| 账号定位与搭建 | B | 账号定位模板、人设档案标准化 |
| 内容生产 | C/D/E/F/G/H | 工业化六步法固化 |
| 流量运营 | I/S | 发布 + 投流联动流程 |
| 直播全流程 | K | 直播 SOP 固化 |
| 用户私域运维 | U | 私域 SOP（承接→分层→复购）|
| 数据复盘迭代 | J/M | 复盘 SOP（回收→诊断→再分析）|
| 合规风控管理 | P/K | 合规 SOP（实时监测+预检+处置）|

> 流程完善目标：让各模块不仅有功能，更有端到端可执行的 SOP 闭环，对齐行业一流产品的标准化能力。

## 10. UI 设计切入时机

UI 分两层切入，避免返工：

**层1 · UI 基座（设计系统 + 布局 + 导航骨架）**
- 时机：**第0步脚手架内完成**（见 §4 第0步 `[实] UI 基座`）
- 依赖：仅依赖全链路主线导航（总体规划 §10），不依赖具体业务数据
- 产出：设计系统（组件/主题/规范）、整体布局框架、基于"创作→分发→分析→投放→用户"的导航骨架
- 理由：全局导航与风格先定，后续模块页面直接套用，不返工

**层2 · 模块功能页面**
- 时机：**对应后端模块完善后逐个跟进**（纳入每模块 `[UI]` 步骤）
- 但阶段1 主链路（B/C/D/E/F/I/L/J）建议在第6步 **I 发布完成后**统一实现第一版页面，避免碎片化割裂；阶段2/3 按模块跟进
- 依赖：后端接口契约已稳定（§6 契约表）
- 理由：UI 对着已稳定接口做，单模块闭环；主链路页面成组出现才有业务意义

**节奏总结**
```
第0步：UI 基座（设计系统 + 导航骨架）
  └─ 第2~6步后端：C→D→E→F→I（数据链路后端跑通）
        └─ 第6步后：阶段1 UI 第一版（B/C/D/E/F/I/L/J 页面）
              └─ 第8步 J 后：闭环 UI 完善
                    └─ 阶段2/3：T/R/K/S/U/W/M、G/H/N/V 模块 UI 跟进（B-core 已在阶段1）
```

> UI 不早于第0步（无基座则风格乱），不晚于对应后端模块（避免接口变更返工）；阶段1 主链路 UI 在第6步 I 后成组落地。
